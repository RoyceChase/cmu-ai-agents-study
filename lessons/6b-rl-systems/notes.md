# 6b · Training 4: RL Systems：课程笔记

来源：[课程官网课件 Lecture 12 · Reinforcement Learning Systems](https://www.cmu-agents.com/slides/lecture-12-rl-systems.pdf) · [官方课表](https://www.cmu-agents.com/#/schedule)。课件核对日期：2026-11-17，讲者 Apurva Gandhi。页码使用 PDF 实际页序。实验数字沿用课件口径，额外解释标为“补充理解”。

## 策略梯度怎样变成一轮系统操作（第 1–8 页）

6a 讨论了优势估计和概率比。执行这些算法时，系统要先让模型与环境交互，再用轨迹和奖励进行一次可微分更新。课件把基本循环拆成五步：

1. **Sample**：推理引擎逐 token 生成。Harness 解析工具调用、执行动作，并把环境观测送回模型。
2. **Verify**：环境或验证器依据轨迹、测试或工具结果给奖励。
3. **Forward**：训练引擎读入已经采到的序列，带梯度重新计算当前策略对生成 token 的 log probability。
4. **Backward**：根据策略损失进行反向传播。
5. **Optimizer step 与同步**：更新训练权重，再按推理引擎的分片方式分发，供后续采样使用。

~~~mermaid
flowchart LR
    I[推理引擎生成动作] --> E[Harness 执行动作并返回观测]
    E -->|继续交互| I
    E -->|轨迹结束| V[验证与评分]
    V --> T[训练引擎重算 logprob 并反向传播]
    T --> W[更新权重与重新分片]
    W --> I
~~~

| 引擎 | 算什么 | 资源重点 |
| --- | --- | --- |
| 推理，例如课件的 vLLM、SGLang | 不跟踪梯度，刚生成的 token 决定下一步输入，随机采样和工具等待穿插 | Decode 吞吐、KV 缓存、连续调度、生成延迟 |
| 训练，例如课件的 Megatron、FSDP2 | 序列已知，可并行重算各位置，保存或重算激活以支持反向传播 | 激活显存、参数与序列分片、有效 token 吞吐 |

补充理解：第 3 步需要当前模型的可微分 logprob。若使用 6a 的重要性比率，还需要采样时的行为策略 logprob 作为分母。两种数来自不同环节，分别随权重和历史条件变化。

## 推理侧：四种优化各省哪一笔开销（第 9–12 页）

| 方法 | 工作方式 | 在 Agent RL 中的作用 |
| --- | --- | --- |
| KV caching | 每次 decode 计算新位置的 Q、K、V，读取历史 K、V，再追加新 K、V | 用缓存内存换少算历史中间状态 |
| Prefix caching | 多请求的 token 前缀相同时复用已有 KV | 同题 GRPO 共享系统提示、工具定义和题面，同条轨迹的后续回合也可共享旧历史 |
| Continuous batching | 每个 decode 步可让已完成请求退出，由等待中的请求补位 | 避免静态批中短请求用完后槽位一直空着 |
| Speculative decoding | 草稿器提出若干候选 token，目标策略并行验证 | 接受率高时，一轮目标模型计算可推进多个 token |

**KV 的容量约束**与 2a 相连。课件用 Llama-3-8B、BF16 为例，约 128 KiB/token。按 32,768 token 算，单轨迹约 4 GiB，64 条约 256 GiB。补充理解：这是未考虑共享或分片前的 KV 量级，模型权重与其他运行开销另计。同题多采样虽然共享前缀，分叉后的 KV 仍要存储。

连续调度常配合 **chunked prefill**，将长提示的预填充分块，减轻它对进行中 decode 的延迟冲击。课件也提到让 prefill 和 decode 分离运行。

**投机解码与训练中的权重变化**：课件以小模型或 MTP 头提出 4 个 token 为例，目标策略一次打分，按接受规则留下可接受的前缀，并在拒绝处按修正分布继续。算法的正确接受与重采样规则保持目标分布。随着 RL 更新策略，冻结的草稿器可能越来越难预测目标输出，接受率下降，课件提出用 SFT 或蒸馏在线更新草稿器。

## 训练侧：激活重算、前缀共享和并行（第 13–15 页）

**Activation checkpointing（激活检查点）**在前向只存若干边界激活。反向走到某层时重算其内部中间值，用完再释放。课件以每层保留输入为示意，完整重算额外增加约一次前向计算，在其估算口径下约为 +33%。也可选择性重算部分模块，减少重算代价。这与推理 KV 缓存刚好体现两种内存与计算取舍。

**训练前缀共享**把同题或同轨迹中的相同历史组织成树。例如四个回复共享提示 P 时，P 的前向只计算一次，每个分支只能看共享前缀和自己的 token。位置编号保持与单独执行该分支一致，各分支梯度累加到共享前缀。它与 4b 的样本 packing 解决不同开销：packing 减少填充，前缀共享减少重复计算。

| 课件案例 | 报告结果及口径 |
| --- | --- |
| ZoRRo | 长提示 GRPO 批次中的重复提示 token 占 80–95%，去重后 actor 更新最多加速 6× |
| AReaL-DTA | 多轮 τ²-bench rollout 以前缀树表示时压缩 9.43×，相对稠密训练的加速最高 8.31× |

**并行的切分轴**。课件图示中，TP 拆同一层的权重或张量计算，EP 将不同 MoE 专家分配到不同设备，CP 按上下文分段。CP 的环形示例里，各 GPU 保留自身 Q，轮转 KV 块来获得其他序列片段的注意力贡献。补充理解：选择哪种并行，取决于限制来自单层计算、专家分布还是长序列，以及切分所需的通信成本。

## 训练与采样之间如何对齐（第 16–17 页）

**权重同步**将训练后的参数发布到推理端。全量同步时，1T 个 BF16 参数约 2 TB，指一份完整参数的量级。推理引擎可能采用另一种并行布局，因此同步还涉及重新分片。第 16 页引用 PULSE，报告其设置里相邻 RL 更新之间约 99% 的参数按 BF16 表示保持不变，可只同步发生变化的部分。比例依赖实际更新与精度。

**Rollout Routing Replay（R3）**面向 MoE。同一历史在推理和训练引擎中经过的数值计算略有不同，路由器就可能选择不同专家。R3 让推理端记录采样时的专家选择，训练端重放路由，以减少由专家路径变化引起的概率不一致。这样轨迹除了 token 和行为概率，还需要对应的路由记录。

## 多轮交互何时能拼成一条训练序列（第 18–22 页）

**Sequence extension** 要求下一轮模型输入保留前一轮已经生成的 token 作为精确前缀，并向后追加。课件用 T 表示任务，A 表示动作，O 表示观测，S 表示压缩摘要。

| 轨迹构造 | 训练样本 | 监督位置 |
| --- | --- | --- |
| 每轮向原历史追加 | 一条完整的 T A₁ O₁ A₂ O₂ A₃ O₃ A₄ O₄ | A₁ 到 A₄ |
| 在 O₂ 后压缩已完成两轮 | 两条，T A₁ O₁ A₂ O₂ 与 T S A₃ O₃ A₄ O₄ | 第一条只训练 A₁、A₂，第二条训练 A₃、A₄ |

示例给同一轨迹所有动作广播同一个优势，任务与观测不直接计损失。压缩后 A₃ 是在摘要 S 的条件下生成的，需要按这个实际历史重算其概率。虽然两条数据都复用了任务文字，重复上下文仍需参与计算。补充理解：压缩可节省长历史的推理开销，也会打断连续前缀。系统需要同时衡量推理长度和训练重算量。

**聊天模板也可能改写历史**。课件以 Qwen 3 / 3.5 的默认模板为例，追加新回合后，旧推理块可能从历史中被移除，导致 token 前缀变化。Tinker、PrimeRL 等课件例子采用专用模板或渲染器保存可追加性。这里讨论的是课件中的接口行为。

## TITO：把实际采到的 token 交给训练器（第 23–24 页）

**Token-In, Token-Out** 直接传递生成前实际输入的 token ID 和模型输出的 token ID。若先把输出转文字，再套模板、重新分词，看起来一样的消息也可能因为分隔符、空白或 token 边界变为不同序列。多个 token 序列还可能解码成相同文本，所以仅凭文字恢复不出原始 token 边界。

补充理解：可以核对某个生成 token 的实际输入前缀、该 token ID、行为 logprob 和损失掩码是否都对齐。TITO 保存的是每次采样的实际条件，遇到上下文压缩仍要按条件改变的位置切分样本。

## 异步 RL：减少空等，同时管理版本陈旧（第 25–27 页）

同步实现可复用同一批 GPU 交替采样和训练。异步实现可把推理和训练放到不同 GPU 上，让 rollout 与权重更新重叠。Agent 会等待工具，轨迹也可能很长。课件给出推理与训练 GPU 数量 **3:1** 的配置例子，实际比例取决于当前瓶颈。

异步流水线需要连续接单和在途请求策略。第 26 页以 SGLang 的暂停与恢复接口示意三种处理：中止请求，撤回运行请求到等待队列并允许重算缓存，或原地暂停并保留可供恢复的 KV。不同方式对浪费的生成、缓存一致性和版本切换有不同影响。补充理解：如果请求能跨权重更新恢复，训练侧还需要知道各段实际由哪个版本生成，才能和 6a 的概率比率对应。

第 27 页把问题扩展到子 Agent 与上下文压缩。补充理解：多代理调用会产生分支，摘要会改变后续看到的上下文。记录需要能把生成段连接到对应父任务、真实输入和采样策略。

## 架构选择：Harness 接入与跨集群运行（第 28–38 页）

**Harness 无关的接入方式**：在 Agent 与推理引擎之间放一个代理服务，兼容不同 harness 调用的推理 API。Agent 继续运行原有搜索、工具与任务流程。代理转发推理请求，并把 token、logprob 和 R3 等数据写入轨迹存储。课件以 Agent Lightning middleman 示意。补充理解：能否直接接入取决于代理是否实现该 harness 使用的协议和消息语义。

| 架构 | 协调位置 | 适用差异 |
| --- | --- | --- |
| SPMD（Single Program Multiple Data） | 每个 GPU rank 运行同一个程序，再按 rank 分到训练组或推理组 | 统一控制通信组、训练和生成，课件示例要求各 rank 按相同顺序创建通信组 |
| 单控制器加独立服务 | 轻量控制器调用推理、Agent、训练、同步、环境与奖励服务 | 可单独扩容、替换实现和独立发布，服务需遵守同一通信协议 |

服务化之后可以随需求增加推理副本。课件用 AstraFlow 示意跨地域和异构资源，把数据采集、训练池和权重管理作为独立组件。另一场景是多策略训练，多个不同模型可在同个多 Agent 任务中协作。补充理解：轨迹应保留每段的策略身份，奖励分配和训练时才能选中对应模型。

## 部署后的在线训练与 Multi-LoRA（第 39–42 页）

**在线 RL** 将真实部署交互连接到训练流水线。第 39 页的 AReaL 2.0 示意中，Agent 调用推理网关，推理侧代理和轨迹存储将执行记录交给训练服务，权重同步再将更新送回推理侧。课件还用 Cursor Tab 与 Composer 作部署案例。

**多租户 Multi-LoRA** 可以在共享基座上同时运行多个独立的 LoRA 训练。第 40 页的八个并发训练与八个串行训练对照展示了整体吞吐收益，单项端到端时间仍需单独看。课件提到 Grouped-GEMM / SGMV 等内核用于处理这种分组计算。Tinker 示例把 Training Client 关联到一次训练运行，把 Sampling Client 关联到一个 LoRA 检查点。下一课进入 Sandboxing and Credential Management。

## 复习与排查：先看瓶颈，再调对应环节（第 43 页）

| 信号 | 如何读异常 |
| --- | --- |
| 训练 reward / pass@1 | 长期持平时查看任务和奖励信号。训练涨、留出评估降时复查验证器及投机轨迹 |
| pass@k | 衡量 k 次采样里至少一次成功的覆盖率。它下降而 pass@1 提升，需检查搜索路径的多样性 |
| Entropy | 突然趋近零可能是探索坍塌，异常跳高时也应查看输出是否退化 |
| 最大重要性权重 | 尖峰可能来自陈旧样本、训练和推理的概率不一致，或少数 token 过度主导 |
| 梯度范数 | 裁剪前梯度异常抬升或有尖峰时，查看比率、奖励及更新稳定性 |
| 平均 staleness | 轨迹的行为策略比当前落后多少个版本，持续上升时查看 rollout 是否跟不上更新 |
| Trainer MFU | 训练设备利用率下降时，查看 padding、样本不均衡与过小的 microbatch |
| Rollout / update / stall 用时 | 分开记录各部分耗时。学习器等待 rollout 时，可检查长轨迹、工具等待和推理调度 |

补充理解：如果观察到学习器空等且权重比率正常，先排查采样和工具链路。若吞吐提升后陈旧度和最大比率一起抬升，应回到版本和概率对齐，再决定是否提高同步频率。两种现象需要看不同环节。
